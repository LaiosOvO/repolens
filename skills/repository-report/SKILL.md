# 仓库业务讲解器

直接由当前 agent 本体执行。本 Skill 只由 Markdown 指令、参考合同和 agent 界面元数据组成；不得调用或依赖任何报告生成程序、渲染器、Python/JavaScript/Shell 脚本或旧 inventory/report 流水线，也不得把本 Skill 包装成另一个程序的入口。

## 输入

从用户请求取得：

- `SOURCE`：源码仓库绝对路径；
- `OUTPUT`：输出目录绝对路径；
- `STAGE`：默认 `all`，也可停在 `context`、`project`、`capabilities`、`implementation`、`engineering` 或 `render`。

缺少 `OUTPUT` 时，在 `SOURCE` 的父目录创建 `{repository-name}-system-explainer/`。不要写入上游源码仓库。

## 固定顺序

完整读取 [pipeline.md](references/pipeline.md)，严格顺序执行：

1. 固定源码身份并探索项目，写 `stages/00-context.md`。
2. 写项目定位、**用户可直接体验的业务功能**、**核心功能有哪些**、核心概念和真实用户旅程到 `stages/01-project.md`。两份清单都是必写正文，不是隐含在导航、架构图或后续章节中：业务功能逐项说“用户做什么 → 系统完成什么 → 用户看见什么”；核心功能逐项说“支撑哪些业务功能 → 实现本质 → 最关键的运行判定”。
3. 完整读取 [coverage.md](references/coverage.md)，穷举用户可见操作、持久业务对象、执行入口和外部边界，写 `stages/02-product-surfaces.md`。
4. 将表面账本逐项归入不限数量的核心业务功能、支撑实现、排除项或未知项，写 `stages/02-capabilities.md`。
5. 对每个已选功能查询 CodeGraph 或等价符号/调用关系，先按 [pipeline.md](references/pipeline.md) 的“运行证据包”写完整 `.evidence.md`，再写融合讲解 `.md`。证据包不闭合时不得用概述性文字代替。
6. 写前后端、进程、Worker、数据与部署的 `stages/04-engineering.md`。
7. 按“项目 → **用户能直接体验的业务功能** → **核心功能有哪些** → **核心架构** → 功能及其底层运行 → 工程地图 → 证据边界”组装 `stages/05-report.md`，再直接写单文件 `index.html`。业务功能回答“产品对外能做什么”，核心功能回答“这些结果由哪些关键机制完成”；两者必须建立显式映射，不能混成代码模块清单。任一清单缺失、核心功能数与实现章数不一致，或某核心功能在第一张图前没有完整自然语言运行叙事，就不得 render。

每完成一个阶段就写产物并汇报耗时。阶段产物存在且源码身份未变化时先验证后复用。没有语义审校循环、自动返修循环或固定重试次数；失败时保留已完成阶段并报告准确原因。

## 功能识别

业务功能必须来自六路并集：产品声明、用户旅程、一等业务对象、真实用户动作、运行/Worker/自动化入口、外部集成与管理配置。CodeGraph 证明实现，不决定业务功能。

功能数量不设上限，但“核心”有严格准入门：必须交付独立业务结果，并闭合公开触发、关键业务转换、权威状态或外部副作用、结果消费者；同时至少属于项目公开主价值、领域对象完整生命周期、决定运行范式的机制或关键外部业务闭环之一。标题必须是用户能理解的动作与结果。health、登录壳、单字段设置、普通 CRUD、路由注册、通用 UI、测试、example 和部署 helper 只能作为某个核心功能的子步骤、支撑实现或排除项，不能独立升级为核心功能。

`02-product-surfaces.md` 必须先为每个可见动作、业务对象生命周期和运行入口分配稳定 `surface_id`。`02-capabilities.md` 必须用 `[纳入]`、`[合并]`、`[支撑]`、`[排除]`、`[待核验]` 将每个 ID 恰好处置一次，并为每个已选功能列出它覆盖的 `surface_id`。“主要模块已处置”不等于“业务功能已覆盖”；单个大文件或单体服务中的多个独立用户结果必须分别进入账本。缺任何一类或任何 ID 未处置就停止，不能开始写功能章节。

配置页、Skill、插件、模型、权限、知识、记忆、协议和外部集成必须追到执行器真正的读取/消费点。只保存了元数据、只有目录或页面、或只有适配入口而未改变运行时行为时，必须标为 `metadata-only`、`catalog-only` 或 `unknown`，不得写成已加载能力。

## 每个功能怎么写

完整读取 [chapter.md](references/chapter.md) 和 [narrative-good-bad.md](references/narrative-good-bad.md)。每个功能把业务作用和底层实现写在同一章。首句必须直接给结论，可以用“简单来说”帮助阅读，但**整句话必须由当前功能的机制指纹生成**，不存在固定后半句或跨仓库复用模板。

随后使用**总—分—总**，只讲一条不重复的因果主链：① 总：一句话说明该功能在系统中的作用和实现本质；② 分：从公开输入开始，连续讲清第一次决策、核心转换、状态提交、下游唤醒和最终输出；③ 总：说明用户最后得到什么、当前实现的主要代价和证据边界。主链讲完后，规则表、状态表、图、失败边界和同类实现对照只补充新信息，不得换一种格式重复同一过程。涉及 Voice 时必须讲清采集 → VAD → ASR → LLM/Tool → TTS → 文本/音频回传与打断。

正文实行**实现术语闭包**。任何会影响技术选型的名词第一次出现时——例如 Leader、Coordinator、Agent、Worker、phase、child、node、edge、router、registry、provider、SDK、协议、checkpoint——必须当场说明：它是什么对象/字段；谁创建；谁读取；读取后触发什么；它明确**不会**自动触发什么。角色名不得替代算法：叫 Leader 不等于会拆任务或调度其他 Agent；叫 Worker 不等于存在远程队列。层级工作流必须逐层说明 workflow、阶段、步骤、依赖和工具各自的粒度。Agent/模型运行章节必须明确是自研循环还是某个 SDK/框架，并列出真实依赖、传输协议和 provider 调用方式；没有 SDK 时直接写“自研控制循环 + 原生/标准协议调用”。

报告是后续 Agent 编码的事实输入，不是自动选型决策器。每个功能必须把实现机制绑定到当前仓库的具体文件、符号、Schema/协议、状态载体和测试，并输出“实现任务地图”：哪些文件/符号分别承担什么责任、依赖顺序是什么、必须保持哪些不变量、用什么测试证明完成。只描述当前实现和客观差异，不替用户下“应选/不应选”结论；用户未提供目标仓库时，不得臆造待修改路径。

“底层如何执行”必须先用自然语言解释，而且这段文字必须在组件表、代码链和第一张图之前。它要连续说清：公开入口收到什么；第一个控制器读哪些字段/状态；它如何生成或选择下一个对象；执行器实际做什么；状态何时提交；谁继续消费；正常/失败/取消如何停止；用户最后看到什么。函数名、类名、文件路径和符号调用链只能放在解释之后作为证据，不能用 `A() → B() → C()` 冒充面向人的机制说明。任何“动态生成”“自动路由”“智能编排”“自动恢复”都必须列出**实际规则**；若规则来自模型 Prompt，必须同时讲 Prompt 约束和宿主代码的确定性校验，不能写成“模型自行决定”。

第一句和主链必须从当前仓库证据**动态推导**，不得套用样例措辞。先完成 [chapter.md](references/chapter.md) 的“机制指纹”：业务作用、控制权、执行形态、核心判定、状态载体、终止条件、可见结果；再用这些字段生成自然语言。除非当前源码命中并证明，否则禁止出现其他报告的组件名、协议字段、控制结构或架构术语。不同仓库即使业务名称相似，也必须重新取证。

对任何“动态生成计划/DAG/工作流”必须先回答第一性问题：**控制权在哪里，源码中是否真的存在确定性生成算法？**如果由模型生成，就用当前仓库实际输入、Prompt、输出结构、校验器和执行器描述；如果由规则/算法生成，就说明遍历、评分、编译或搜索规则；如果是混合模式，就逐段标出控制权转移。禁止复制某个样例的句式，也禁止把“模型返回结构化结果”包装成未被源码证明的智能算法。

对决定项目技术路线的核心功能，不能停在一次主链。先列出读者最需要回答的 3–5 个问题，再按 [chapter.md](references/chapter.md) 的“核心机制深挖”回答：设计范式及替代方案、**生成/选择/调度规则**、核心类型目录、静态定义如何变成运行时行为、状态连续性、五层机制解释。简单 CRUD 或外围功能不强行套用这些小节。

核心功能在可联网且能找到一手来源时，增加“同类项目的对应功能怎么做”客观对照。优先使用同仓库已声明竞品、用户提供的参考仓库，以及框架官方文档/源码；有证据时比较至少两种真实范式，分别写清控制权在哪里、图/计划何时生成、边如何决定、状态如何持久化、失败如何恢复。不给排名、推荐或代选结论；外部参考不能替代当前仓库源码证据。无法获得一手来源时标记“本次未做同类实现对照”，不阻断当前源码解释。

图必须是当前功能的真实组件交互，不能只是四格文字卡。采用 [html.md](references/html.md) 的深色高对比技术图合同：参与者、控制器、执行器、状态和外部系统用不同语义描边；主链实线、可选/异常链虚线；每个节点只写“角色 + 动作/状态”，不塞段落。Mermaid 节点使用短 ID 和带引号标签；代码路径、函数名与特殊字符只放标签，不作节点 ID。密集图改为 `flowchart TD`，并拆成主链与异常链。

## HTML

完整读取 [html.md](references/html.md)。直接把最终 Markdown 内容写进自包含 HTML；仅 Mermaid 运行库允许 CDN。必须有固定侧边栏章节导航，正文 13px，每个功能章就地包含交互图、文字解释、组件表和源码证据。不要先列一遍功能、后面再重复一遍实现。

## 完成门

在汇报完成前逐项检查：

- 非技术读者能用一句话说出项目是什么；
- “这是什么项目”后按顺序出现用户业务功能、核心功能自然语言总览和核心架构；核心架构明确前端/调用方、后端/运行时、状态、Worker/外部服务如何交互；仓库不存在前端时必须直说；
- “这是什么项目”后先有用户视角业务功能清单，每项用自然语言写清用户动作与可见结果；随后逐项给出核心功能自然语言总览，并明确业务功能由哪些核心机制支撑；
- 核心业务功能没有数量上限且覆盖账本闭合；
- 产品表面账本中每个 `surface_id` 恰好处置一次，所有独立用户结果均已纳入功能或显式标为待核验；
- 每个功能和对应底层运行在同一章节；
- 所有管理面配置都追到运行时加载器和执行器消费点，未接通者没有被写成已实现能力；
- 至少所有“核心机制”功能都回答设计范式、类型目录、定义到运行时、状态连续性与五层深入；不适用时说明原因；
- 每个核心功能都存在闭合的运行证据包，并在图之前用自然语言解释代码执行；所有“动态/自动”能力都列出具体规则；
- 每个影响选型的实现术语都已闭合到对象/字段、创建者、读取者、触发行为和非行为；角色名、层级名或框架名没有被当成解释；
- 每个功能的主链只叙述一次；规则表、步骤、图和状态表没有同义复述；
- 能获得一手来源时，核心功能有同类项目实现机制对照，但没有替用户做推荐/排名结论；
- 每个功能都有可交给编码 Agent 的实现任务地图：文件/符号、复用点、改造点、不变量和建议测试均闭合；
- 每张 Mermaid 都实际渲染，无 `Syntax error in text`；
- 侧边栏可跳转，源码证据路径存在；
- 输出包含阶段 Markdown、`index.html` 和 `performance.md`；
- Skill 执行过程没有调用报告生成程序、渲染器或任何辅助脚本；CodeGraph 只负责源码关系取证，当前 agent 本体负责全部归纳、写作和 HTML 组装。

最终返回所有产物的绝对路径、功能数、各阶段耗时、复用项和待核验项。
