# 因果主链 Good / Bad Case

这些例子只说明质量判定，**不是可复制模板**。实际报告必须换回当前仓库的机制指纹与源码事实。

## Good：一条主链只解释一次

> 用户提交待处理对象后，入口先验证身份与输入版本，再把对象转成带稳定 ID 的任务记录。调度器只领取状态为 pending 且租约已到期的记录；Worker 成功提交产物后，以同一事务把任务改成 completed 并写入结果引用，随后发布完成事件。等待方收到事件后读取已提交结果并返回给用户；取消、租约过期与重试只改变这条主链的边界，不另造第二套执行路径。

这段合格，是因为它从输入推进到输出，控制权、判定、状态提交、下游和终止都出现了。后面的表格只应列“租约过期/取消/重试上限分别如何处理”，图只显示参与者与主/异常路径。

## Bad：只替换名词的万能段落

> 系统收到请求后进行校验和处理，接着更新状态并调用下游，最后返回结果。失败时会重试或降级。

这段可套到任何功能：没有真实控制者、判定字段、中间对象、状态载体或终止条件。替换“请求/结果”为“音频/文本”“目标/任务”仍不增加证据，必须拒绝。

## Bad：同一主链重复三遍

正文已经完整写了“提交 → 校验 → 入队 → Worker → 回传”，随后步骤列表再次列同样五步，规则表又把五步逐行改写，流程图仍只画同样五个框。这会增加阅读长度而不增加技术选型信息。

修复方法：保留正文作为唯一因果叙事；删除步骤列表；规则表改为正文未覆盖的判定/失败矩阵；流程图增加角色、状态边界与虚线异常，让它承担视觉压缩而非第三次讲故事。

## 每章发布前自检

1. 隐去业务名词后，这条主链是否仍能套到其他章节？若能，补真实判定、状态和终止事实。
2. 与本报告其他章节相比，至少两个机制字段是否有源码支持的实质差异？若没有，考虑合并。
3. 删除表格和图后，正文是否独立完整？恢复它们后，是否只增加新维度而不重复正文？
