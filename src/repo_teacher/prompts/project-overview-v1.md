## 项目定义与产品主轴

- one_liner 第一词句就给出项目定义、主要用户与最终结果。
- 先读 product_navigation 中的 README 和项目元数据确认作者宣称的定位；具体实现仍必须由
  非文档 source_refs 证明。
- core_product_axes 只能有 1–4 条产品主轴，是用户认识产品时最先讲的高层分类，不是功能数量上限。
- 产品主轴只是分类；每个已确认业务功能都必须在页面直接可见。
- supporting_capability_ids 只表示阅读优先级较低的独立业务功能，不得伪装成运维项。
- capability_order 必须是这些 id 的精确全排列：`$capability_ids`。

## 端到端交互

- 每条 end_to_end_flow 都会画成交互图，必须说明数据、控制权与状态怎样移动。
- 每一步写成“参与者/模块：收到或读取什么 → 做什么判断/处理 → 改了什么状态 → 交给谁”。
- 第一项说清输入来源，最后一项说清用户可见输出。
- 跨主轴必须写清控制权与数据的每次交接，不能用一个技术名词代替中间过程。
- 如果一次动作由异步执行器完成，必须说明提交、权威状态、调度/租约、执行、副作用、
  事件/结果回传分别由谁负责。没有证据的环节写未知。
- 如果能力会生成或发布产物，必须说明本地还是远端执行、提交的数据形态、执行引擎、持久化位置、
  日志与失败状态、最终可见结果怎样回传；不能根据按钮文案推断实现。

- engineering_structure 直接判断 monorepo、单包或多服务，以及 DDD、分层、模块化单体、

- 不得因为出现 domain 目录就判 DDD；必须根据依赖方向、业务规则放置和端口/适配器边界说明理由。

- code_organization 覆盖重要产品源码目录并说明职责、所属层、边界；不枚举 assets、fixture、vendor。
