# 人类可读代码索引：机制讲解技术决策

## 结论

产品形态选择 **CLI 主产品 + 内置模型 Prompt + 结构化报告合同**。

用户运行：

```bash
repo-teacher report /path/to/repository --output /path/to/report
```

主要交付是 `index.html`；同时保留 `index.json`、`analysis-pack.json` 和
`human-report.json`，用于证据核验、重生成与后续比较。

## 为什么这样选

参考项目分别解决了不同层次的问题：

- DeepWiki：采用“项目 → 功能 → 实现证据”的分层下钻，而不是把文件树当首页。
- PocketFlow 教程：采用总—分—总与具体任务故事，让人先理解为什么和怎么运行。
- Sourcegraph / Serena：源码符号、引用和精确位置只作为可点击证据，不冒充产品功能。
- CodeBoarding / RepoAgent：保留结构图、依赖关系和增量失效思路，支撑证据更新。
- GitHub code-tour、codebase-onboarding 等 Skills：吸收“按目的组织阅读路线”的输出合同。

Skill-only 适合约束一次 Agent 会话，但不能稳定提供版本化 CLI、机器可读中间产物、
离线校验和可重复发布。纯代码规则适合扫描语法事实，但不能可靠判断一个仓库真正的产品功能、
存储语义、查询算法或设计取舍。因此两者都不单独作为主产品。

## 生成管线

1. **确定性证据索引**：扫描文件、符号、关系、测试与固定版本身份，形成 canonical index。
2. **分析证据包**：把可引用 evidence ID、功能候选、模块和阅读路径交给模型。
3. **模型语义理解**：Codex 读取证据包，并在需要时继续读仓库源码，归纳真实产品功能。
4. **强制机制合同**：每个功能必须输出 `mechanism_model`，缺一项就拒绝发布。
5. **证据闭包校验**：所有 feature/evidence ID 必须来自 canonical index；未知行为降级到边界或未知项。
6. **人类报告渲染**：采用“总—分—总”。功能标题后的第一句直接说明本质构造与主数据流，再展示 30 秒结论和一次运行主线；机制、难点、复用边界分成三组按需展开，最后用本质与复用判断收束；源码入口与调用关系折叠在最后。

## 页面阅读层级

默认视图先给出“本质一句话”，再回答两个问题：

1. 这个功能是什么、为什么存在、底层机制一句话是什么；
2. 一次任务从谁触发到谁消费，按什么因果顺序运行。

其余内容使用渐进披露：

- 第一层：底层机制、状态读写、查询、循环、路由和结束条件；
- 第二层：真正难点，固定按“运行过程 → 不变量 → 天真实现失败 → 设计取舍”；
- 第三层：支持边界与 `take / adapt / avoid / verify`；
- 最后一层：源码、行号、静态关系和证据缺口。

难点不再使用四个并排的大卡片。桌面与移动端都使用线性因果顺序，证据与迁移问题再折叠一层，避免首屏一次出现全部信息。

## 每个功能的强制内容

每章必须回答：

1. 存什么 / 数据结构是什么。
2. 如何写入，何时提交，失败是否留下可重试的原始数据。
3. 如何读取或查询，包括 gate、过滤、召回/搜索、排序、Top-K 与结果合并。
4. 核心控制循环是什么；如果不是循环，必须明确说明一次调用结束。
5. 决策、路由或就绪规则是什么。
6. 何时结束，有哪些硬上限。
7. 哪些能在运行前或运行中动态变化。
8. 用至少三个因果步骤串起一个具体例子。

涉及存储时必须区分：

- source of truth；
- 原始事件；
- 派生事实/摘要；
- 可重建索引或镜像。

不涉及存储或查询的能力，也必须明确写“无独立存储层”或“无查询层”，不能留空。

## 明确拒绝的方案

### 不用正则识别产品功能或机制

正则不能证明 `facts` 是长期事实、`episodes` 是带时间经历，也不能证明 `route(state)`
怎样决定下一节点。功能语义由模型结合源码与证据理解；代码只做结构校验、ID 闭包和渲染。

底层语言扫描器可以继续使用 AST、LSP 或保守 lexer 提取语法事实，但这些事实不能自动升级成
“产品功能”或“底层机制”的结论。

### 不把源码入口作为报告主线

`main()`、route、class、文件路径只回答“去哪里核验”，不回答“系统提供什么能力、为什么这样设计”。
首页和功能章节禁止用程序入口替代功能名。

### 不只交付一份人工修改的 HTML

HTML 必须由同一个 CLI 管线从版本化索引和结构化 narrative 生成，保证未来可用于其他仓库。

## Waku 验收样本

Waku 只用于验证通用合同，不在 CLI 中写死为唯一输入。当前报告对 9 个能力逐章输出完整机制。

- Memory：`state.db`、`chat_log`、facts、episodes、FTS5 派生索引、retrieval gate、Top-K 与结果合并。
- Agent Loop：显式 `for iteration`、`tool_uses` 决策、observation 回填和 `max_iterations`。
- Graph：内存 topology、wave 就绪计算、整波提交、join、`route(state)` label 与运行中拓扑边界。
- 其余 Gateway、Voice、Tools、Providers、Dashboard、Eval 也使用同一强制合同。

## 当前边界

- 模型语义结论必须由证据 ID 约束，但静态证据仍不能证明真实性能和生产可靠性。
- 自动模型生成的质量还需要跨仓库 benchmark；Waku 不是唯一验收仓库，只是本轮快速样本。
- 当前 CLI 默认调用 Codex；未来可增加 provider adapter，但不能降低相同的 schema 和证据门。
