# ADR-0002：单项目人类报告的内容合同

- 状态：Accepted
- 日期：2026-08-10
- 范围：Repo Teacher 生成的每个单项目报告

## 决策

报告的目标不是展示索引器找到了多少入口、符号和文件，而是让读者先理解：**这个项目提供哪些功能、每个功能靠什么机制实现、哪些代码值得作为自己的实现参考。**

HTML、Markdown、JSON 只是不同视图；它们必须来自同一个内容模型。第一期以 HTML 作为人类主入口，Markdown 保留研究过程，JSON 承载机器闭包与后续 Skill 导出。

## 固定叙事顺序

### 0. 内容口径

先告诉读者内容来自哪里、能证明到什么程度：

- 功能语义来自已审阅的项目 profile；
- CLI 核对仓库身份、源码路径、行范围、内容哈希和跨产物闭包；
- 静态源码不能证明的运行时行为必须写为未知；
- 单项目报告不替读者做跨项目排名。

### 1. 30 秒看懂

回答四件事：

1. 这是什么产品或框架；
2. 它解决谁的什么问题；
3. 它以什么产品形态交付；
4. 为什么值得继续看。

首屏不出现入口函数、路由列表、类清单或大段架构术语。

### 2. 功能地图

列出 5–12 个用户或开发者能够感知的一级功能。每张卡只回答：

- 功能名称；
- 它给使用者提供什么；
- 点击后可以下钻到对应实现说明。

入口、文件和符号不能被包装成“功能”。

### 3. 逐功能实现

每个功能先生成一张**难点地图**。索引器不能把文件多、函数长或入口深直接当作难点；候选必须由源码和测试证据支持，并绑定到这个功能的真实执行路径。

难点发现至少检查：

- 并发、锁、wave/barrier、队列和共享状态；
- 状态合并、冲突、缓存、checkpoint、迁移和一致性；
- router、条件分支、循环、预算与终止条件；
- retry、fallback、rollback、幂等和故障恢复；
- 模型/协议/进程/网络等边界适配；
- 权限、沙箱、秘密、外部副作用和人工审批；
- 高 fan-in/fan-out、跨模块调用和动态分派；
- 针对碰撞、竞态、失败、漂移和恢复的测试；
- 源码中解释“为什么这样设计”的约束与 trade-off 注释。

每个难点必须输出：

1. 难点是什么，不使用空泛形容词；
2. 为什么它比普通顺序代码更难；
3. 它维护的 state、依赖和不变量；
4. 真实运行过程；
5. 失败路径和边界条件；
6. 当前设计选择与代价；
7. 对应测试、源码和置信度；
8. 复用或修改时必须保留的合同。

完成难点地图后，每个功能再按相同顺序回答七个问题：

1. **提供什么**：用户最终得到什么能力；
2. **何时发生**：由谁、在什么场景触发；
3. **如何流转**：触发者 → 接管者 → 核心机制 → 输出 → 消费者；
4. **靠什么实现**：关键机制和技术，不做依赖名堆砌；
5. **代码在哪里**：入口、核心、状态、适配器、测试的推荐阅读顺序；
6. **怎么借鉴**：可直接借鉴、需要改造、不要照搬；
7. **证据与未知**：源码范围证明了什么，仍有何运行时或部署未知。

代码模块按阅读顺序展示；源码路径和行号是叙述的证据，不是叙述本身。

### 4. 项目整体判断

逐功能讲解后再收束到项目整体：

- 架构特征；
- 主要优势；
- 主要限制；
- 适合作为什么类型的参考；
- 继续横向比较时应记住的问题。

这里仍然不做跨项目排名，不替读者决定采用哪个项目。

### 5. 证据附件

主 HTML 只显示必要证据；完整闭包由附件承担：

- `report.json`：功能语义；
- `evidence.json`：源码范围、哈希和可点击 URI；
- `modules.json`：功能到模块以及推荐阅读顺序；
- `manifest.json`：整包文件哈希与 generation identity。

### 6. 结束总结

用 3–5 条结论回答：看完这个项目后，读者在后续横向比较中应该记住什么。

## 明确不进入主叙事的内容

- 全量入口、路由、类、函数、依赖清单；
- 未分组的源码路径或代码块；
- Star 数量驱动的“推荐”；
- 自动替读者完成跨项目技术选型；
- 没有源码或测试证据的运行时断言；
- 还未进入实现阶段的详细模块、协议和数据库设计。

## 参考项目与 Skill 的采用关系

- **DeepWiki**：采用“概览 → 功能层级 → 下钻”的信息结构；
- **PocketFlow Code2Tutorial**：采用由浅入深的教学顺序，不采用把生成文案当静态事实；
- **GitHub Code Tour**：采用有顺序的源码锚点与首尾叙事闭环；
- **codebase-onboarding Skill**：采用 Overview / Architecture / Common Tasks / Where to Look 的读者问题；
- **SourceBridge**：采用 claim 与精确证据分层；
- **CodeBoarding / RepoAgent**：采用结构化代码关系和增量影响思路；
- **Serena**：未来作为实时语义导航适配层，不作为报告内容模型；
- **Skill 规范**：采用 progressive disclosure；确定性生成仍由 Go CLI 完成，Skill 只做薄入口。

## 验收标准

1. 首屏不依赖代码术语也能说明项目价值；
2. 每个一级功能都有“提供什么”，且不是入口/文件名；
3. 每个功能都完整回答七个固定问题；
4. 源码证据能按建议顺序点击阅读；
5. 复用建议明确分为直接借鉴、需要改造、不要照搬；
6. 未知项可见，不用肯定语气掩盖证据缺口；
7. 页面结束有项目整体总结；
8. 主页面没有自动排名或替用户做跨项目选择；
9. HTML、report、evidence、modules、manifest 是同一 generation 且可重放验证；
10. 390px 和桌面视口无整页横向溢出。
11. 每个功能至少给出一张有证据的难点地图；没有发现难点时必须明确写“未识别到”，不能由模型补写。
12. 每个难点都解释 state、不变量、运行过程、失败路径、trade-off 和测试证据。
