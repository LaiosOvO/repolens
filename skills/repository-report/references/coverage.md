# 产品表面全量覆盖合同

本阶段解决“候选生成器没提出的功能，后续阶段永远看不见”的问题。它只枚举与归纳当前仓库事实，不使用仓库名、领域关键词、路径正则或固定功能清单决定结论。

## 第一步：枚举表面，不提前合并

从以下七路取并集：

1. README、官方文档、manifest 与导航中的产品承诺；
2. 用户可见的页面动作、表单提交、命令、快捷操作和客户端事件；
3. API、IPC 或目标仓库自身的命令行中，会创建、变更、执行、发布、取消或删除业务对象的入口；
4. 持久化的业务对象、状态机、消息、任务、产物与关系；
5. Worker、调度器、trigger、webhook、定时器和其他无人值守执行入口；
6. 外部服务、协议适配、组队/协作、管理配置、Skill/插件/知识/记忆/权限等可能改变运行行为的表面；
7. **工程封装边界**：workspace 成员与子包——Cargo workspace crate、Go module、pnpm/lerna/Bazel/npm package、Maven/Gradle 子模块、一级功能目录——以及它们的**作者自述**（包级 doc 注释、description 字段、子包 README）。作者愿意为一个能力单开一个封装单元，通常意味着一个可独立讲述的能力面；即使 README 与文档一字未提，每个成员单元的自述意图也是一条原始观测，必须进入枚举。

路由表、菜单和文件树只负责“帮助枚举”，不能直接判定业务功能。封装边界同理：它是候选来源，不是功能判定——每个成员单元仍要走 surface 归并与核心准入门，纯工具型 crate（构建辅助、测试夹具、通用 utils）照常落 `[支撑]` 或 `[排除]`。同一个大文件中可能有多个独立表面；多个目录也可能只实现同一个用户结果。

先为六路中每个原始观测项分配 `origin_id`，再将一个或多个 origin 归并为 `surface_id`。原始观测项至少保存类别、公开名称/动作、源码位置和归并理由。阶段末尾必须给出六路各自的 `origin_count`、合计数、已映射数与未映射 ID；合计数与已映射数不等就停止。

大仓库可按模块或图社区分批枚举，但每批必须保留 origin ID，最后作 exact-once 合并。不得因为模型上下文有限而只取“前 N 个”且不声明；未读完时记录未完成分批并不得进入 capabilities。

## `02-product-surfaces.md` 必填格式

| 字段 | 内容 |
|---|---|
| `surface_id` | 在本次源码快照中稳定、唯一的 ID |
| `origin_ids` | 来自六路原始枚举的非空 ID 集合 |
| 使用者与目标 | 谁为了什么结果使用它 |
| 用户动作与输入 | 用户/调用方真正提交什么 |
| 可见结果 | 用户或下游能观察到什么 |
| 业务状态 | 创建、修改或读取的业务对象/状态 |
| 入口证据 | 页面/API/命令/事件的路径、符号和行范围 |
| 执行闭环证据 | 执行器、状态提交、结果消费者的路径、符号和行范围 |
| 支持边界 | `verified-runtime` / `verified-local` / `metadata-only` / `catalog-only` / `external` / `unknown` |

`verified-runtime` 要求入口、执行、状态和结果消费闭合。`verified-local` 表示仅当前本机/单进程闭合。`metadata-only` 表示字段可保存或展示，但执行器未读取。`catalog-only` 表示只有目录/选项/空适配器。`external` 表示依赖仓库外实现。`unknown` 表示当前证据不足。

账本之后必须再生成一份**用户视角业务功能清单**。它不是把每个 surface 原样抄成卡片，而是按用户目标归组，逐项用完整自然语言回答：用户在什么界面/入口做什么，系统实际完成什么，用户看到什么结果，当前支持边界是什么。创建、配置、执行、协作、发布/部署等如果形成不同用户旅程，必须分别可见；简单 CRUD 仍合并到其领域旅程。每项同时列出支撑它的 `surface_id` 与核心 capability，确保“用户看到的产品”能下钻到“底层机制”。

## 第二步：从表面归并业务功能

只有同一使用者目标、同一权威业务状态、同一结果消费者和同一失败边界共同闭合时，才能将多个 surface 归为一个 capability。满足任一下列条件时保留为独立功能或清晰子功能：

- 有独立的用户动作和可见结果；
- 有独立持久对象、成员关系、生命周期或权限边界；
- 执行位置、协议、控制者或失败语义对技术选型产生实质影响；
- 是项目的主要采用理由，而不是只被另一功能内部调用。

### 核心功能准入门

`surface` 全量枚举用于防漏，不代表每项都要生成核心章节。一个核心功能必须同时满足：

1. 有用户/调用方能识别的独立业务结果，不只是“对象已保存”“页面可打开”或“接口存活”；
2. 从公开触发能追到关键业务转换，并最终到达权威状态、外部副作用或下游消费者；
3. 至少满足一项：项目公开主价值、领域对象完整生命周期、决定运行范式的控制机制、关键外部业务闭环；
4. 移除它会让项目的一条主要用户旅程或采用理由不成立。

普通 CRUD 只有在共同表达同一个领域对象的完整生命周期时，才能合并为该业务功能的子功能；单独的 create/list/update/delete 不各自成章。health、登录壳、导航、样式、通用表单、路由汇总、开发工具、example、测试和部署 helper 默认进入 `[支撑]` 或 `[排除]`。如果某个看似基础的能力确实决定核心业务结果，必须用入口、转换、状态和消费者证据证明例外，不能仅凭页面名称提升。

`02-capabilities.md` 每项必须列出 `surface_ids`，并先列“核心准入证据”：独立业务结果、关键转换、权威状态/副作用、结果消费者、主旅程影响。文件末尾生成 exact-once 核对表：每个 `surface_id` 只能出现在 `[纳入]`、`[合并]`、`[支撑]`、`[排除]`、`[待核验]` 中一次。任何一项未出现或重复出现都停止后续阶段。

### 集成域不得压扁成单个功能

多个工程单元围绕同一宿主或同一对外协议聚成一组（协议定义、传输适配、守护进程、同进程客户端、桥接工具各成一个包）时，这一族整体只是一个**集成域**，不是与其他业务功能对等的单条功能：

- 必须枚举该域通过协议**实际暴露的每个子能力**——每个请求类别、事件类别或工具类别至少产生一条候选 surface（谁触发、返回什么、落什么状态）；
- 域内每个成员单元的声明意图单独处置，不得因“同属一个域”合并进一条不透明的功能条目；
- 域内只有装配或派生代码、没有独立用户结果的成员（纯宏、纯类型定义、测试夹具、传输桥接）标 `[支撑]`；
- 集成域最终在账本中的形态是：一个命名清晰的域条目 + 一张显式子能力清单，子能力各自走准入门。

## 第三步：配置到运行时接线

对每个包含配置、模板、Skill、插件、知识、记忆、权限、模型或协议适配的功能，evidence 必须有一行跟踪：

`UI/API 收集字段 → 校验/默认值 → 持久化位置 → 运行时 loader → 执行器消费点 → 可见行为`。

某环没有源码证据时在该环写“未证明”，并将支持边界降级。不得因为页面能保存、数据库有字段、仓库有协议入口或其他模块有 DAG，就宣称当前执行链已加载该配置、通过该协议运行或使用该 DAG。

## 第四步：协作与外部集成语义

对任何群组、群聊、多 Agent、Worker 群、工作流协作或外部 IM，必须逐项回答：

1. 成员类型是人、Agent、Worker 还是混合；成员关系是否形成授权边界；
2. 无显式选择、单选和多选时分别由谁执行；
3. 是串行、并行 fan-out、固定 DAG、动态规划还是事件订阅；
4. 参与者是否看到彼此中间结果，是否有共享状态或消息交换；
5. 结果是固定包装、代码聚合还是模型二次综合；
6. 部分失败、取消、进度、重试和幂等怎样处理；
7. 若声称是真实 IM，外部 provider adapter、身份、推送/收取链和持久消息 ID 在哪里。

同仓库其他子系统存在调度器、DAG、ACP/MCP 或消息表，不能证明当前协作链使用它。必须找到当前公开入口到该机制的真实调用/数据依赖。

## Good / Bad

**Good（封装边界）**：仓库在 packages/ 下并排存在「可执行代码环境」「云端任务管理」「把本产品作为工具暴露的 server」三个独立包，各自 doc 注释声明了意图；README 只宣传 CLI 主功能。账本仍把三个包各列为候选 surface 并走准入门——文档没宣传的能力不等于不存在。

**Bad（集成域压扁）**：把「给外部宿主暴露能力的协议服务族」（协议 schema、传输适配、守护进程、同进程客户端、桥接工具共 9 个包）压成一条「IDE 集成」功能，既没枚举该协议暴露的子能力（每个请求/事件类别），也没处置每个成员单元；或走向另一极端，把每个包机械升级成业务功能而不走准入门。

**Good**：一个单体服务中同时有“创建执行者”、“直接对话”、“建立组并发执行”和“插件设置”。账本将四个表面分别枚举；进一步查明“插件设置可保存，但执行器使用固定工具清单”，因此标为 `metadata-only`。

**Bad**：因为单体服务所在模块已被某一功能覆盖，就宣称整个产品已覆盖；或因为看到群聊页面与 DAG 调度器，就宣称群聊通过 DAG 做多智能体协作，却没有从群消息入口追到调度器。
