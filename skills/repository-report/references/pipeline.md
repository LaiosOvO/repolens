# 纯 Skill 阶段合同

| 阶段 | 读取 | 必写产物 | 通过条件 |
|---|---|---|---|
| context | Git 身份、README/docs、manifest、工程树 | `00-context.md` | 项目声明、用户表面、主要模块和外部系统均出现 |
| project | context + 少量关键源码 | `01-project.md` | 一句话本质；非空“用户能直接体验的业务功能”清单；非空“核心功能有哪些”清单；业务↔核心映射；核心架构与真实旅程 |
| surfaces | context + project + 用户动作/对象/执行入口 | `02-product-surfaces.md` | 六路 origin 枚举无静默截断；每个 origin exact-once 映射到有入口、状态、结果和支持边界的 surface |
| capabilities | product surfaces + 因果关系 | `02-capabilities.md` | 功能不限量；所有 surface ID exact-once 归入/合并/支撑/排除/待核验 |
| implementation | 单个功能 + 对应关系查询 + 核心功能同类框架官方资料 | `03-implementation/NN-*.evidence.md` 与 `.md` | 一功能一证据包一融合章节；配置到运行时接线与图前自然语言叙事闭合 |
| engineering | context + 跨功能事实 | `04-engineering.md` | 前后端、目录、进程、Worker、数据、部署 |
| render | 上述全部 Markdown | `05-report.md`、`index.html`、`performance.md` | 两份功能清单可见；每个核心功能都有图前自然语言因果叙事；导航、证据与待核验项闭合 |

## Context

1. 固定 commit/branch/remote；非 Git 仓库记录目录 manifest。
2. 先读产品声明与顶层工程树，不遍历依赖、构建产物、二进制和密钥文件。
3. 仓库存在 `.codegraph/` 时先使用 CodeGraph；否则使用语言 AST/LSP、引用搜索和源码阅读建立等价关系事实。
4. 分别收集：用户旅程与业务对象、业务入口与可见结果、Worker/状态/集成/部署。

## Capabilities

必须先完整读取 [coverage.md](coverage.md)并生成产品表面账本，再做能力归并。每个能力必须有独立用户价值、开始条件和可见结果；模块或页面不能单独成为功能。按用户认知顺序排序，而不是按目录顺序。

覆盖单位是 `surface_id`，不是目录、模块或已生成候选。一个单体 API 模块可以包含多个独立业务生命周期；只处置模块名不能证明核心业务已覆盖。全量 surface 用于防漏，不等于全部写成核心功能；必须按 [coverage.md](coverage.md) 的核心准入门把简单 CRUD、壳页面和工程支撑合并或排除。进入 implementation 前必须核对账本总数与 exact-once 处置总数相等，且没有未解释的核心用户结果。

`01-project.md` 必须实体化两份清单，禁止用“详见后文”、侧边栏链接或架构图代替：

```markdown
## 用户能直接体验的业务功能
1. **{用户目标}**：{在哪里提交什么}；{系统实际完成什么}；{用户看见什么}；{当前边界}。

## 核心功能有哪些
1. **{核心功能}**：支撑 {业务功能编号}；{实现本质}；{决定结果的关键规则}。
```

业务功能数、核心功能数、implementation 正文数必须在 `05-report.md` 顶部记录。核心功能数与 implementation 正文数不一致时停止 render。

## Implementation

对每个能力单独查询，不重扫整仓。查询入口、核心转换、状态读写、路由条件、循环/并发、Worker 交接、失败与结束。只读取查询命中的必要源码。各能力可并发取证和写作，但最后由当前 agent 统一语气与结构。

### 运行证据包

每个 `.evidence.md` 在写正文前必须固定输出以下十二项；这是一次性阶段门，不是循环审校：

1. **业务表面闭包**：本功能覆盖哪些 `surface_id`，子功能和未纳入表面是什么。
2. **公开入口与输入**：API/命令/事件、输入结构、默认值。
3. **对象与配置事实**：Schema、枚举、注册表、协议、业务对象字段、创建时复制什么与默认什么。
4. **配置到运行时接线**：对每个可改变行为的字段追踪 `收集 → 校验 → 持久化 → loader → executor 消费 → 可见行为`；标出 `verified-runtime/metadata-only/catalog-only/unknown`。
5. **生成规则**：节点/任务/候选/计划如何产生；模型 Prompt 与代码硬规则分开。
6. **选择与路由规则**：分支条件、排序/打分、依赖和默认/无匹配行为。
7. **执行算法与位置**：当前源码实际使用的循环、单遍/多遍解析、编译、搜索、拓扑、队列、状态机或并发屏障，以及在浏览器、客户端、服务端、Worker 还是外部平台运行；不存在时明确写不存在。
8. **协作/集成语义**：涉及多参与者时说清路由、并发/依赖、中间结果互见、聚合和部分失败；涉及外部集成时找真实 adapter 和收发链。
9. **状态与数据**：读取、写入、索引、checkpoint、可见时机与生命周期。
10. **失败与恢复**：校验失败、重试、级联、取消、超时、预算和幂等边界。
11. **输出与消费者**：返回结构、事件、持久化结果、谁继续使用。
12. **实现对照与编码地图**：有一手来源时，客观对照至少两个同类框架/项目的运行语义；将当前实现责任绑定到文件、符号、合同、不变量和现有测试。不输出推荐/排名结论；无一手来源时不阻断当前源码讲解。
13. **实现术语闭包**：把正文会出现的每个关键角色、层级、运行时和协议词列成 `术语 → 数据/字段 → 创建者 → 读取者 → 触发行为 → 明确不触发的行为 → SDK/框架/协议`。缺任一列时，正文不得只靠这个词解释机制。

再从十三项证据中提炼一条**唯一因果主链**：`公开输入 → 第一次决策 → 核心转换 → 状态提交 → 下游消费 → 最终输出`。正文、步骤表、规则表和图必须共享这条主链；每一事实只能选择一个位置完整解释，其他位置只引用或增加新维度，禁止同义改写三遍。

每项都要附仓库相对路径、符号和行范围。核心项若源码不存在，写“源码未证明”，正文必须降级为未知；不得借 README 或竞品行为补齐当前实现。

### 机制指纹：先分类，再写第一句

每个功能在 evidence 文件中先填写以下字段，不能从其他项目复制：

| 字段 | 要回答的问题 | 证据来源 |
|---|---|---|
| `business_role` | 它替用户完成什么结果，在整个系统中负责哪一段 | 产品表面 + 运行结果 |
| `control_locus` | 核心决策由确定性代码、LLM、人工、配置还是外部服务控制 | 条件分支、Prompt、协议、事件 |
| `execution_form` | 循环、状态机、DAG、流水线、事件订阅、队列 Worker、存储检索或其他 | 控制流与状态结构 |
| `decision_predicate` | 继续、路由、选择或完成真正读取什么事实 | `if`/match/schema/router/scheduler |
| `state_carrier` | 中间状态由什么对象、表、队列、消息或 checkpoint 承载 | 写入与读取点 |
| `termination` | 正常、失败、取消、超时分别何时结束 | 终止分支与返回值 |
| `visible_result` | 最终交付给哪个消费者什么结果 | 返回、事件、持久化产物 |

正文第一句由这七项合成，不使用固定模板、槽位填充句或样例答案。先用业务语言说作用，再用最少必要技术词说执行本质和关键判定；具体句式由当前证据决定。

反硬编码检查：把当前仓库名称、符号和证据临时遮掉后，如果第一句仍与上一份报告完全相同，说明机制没有重新推导，必须返回 evidence 阶段。

### 动态首句的 Good / Bad Case

**Good Case**：先从本功能证据填满七个机制字段，再删去函数名和路径，用该功能自己的“业务结果 + 控制权 + 核心判定”写首句。换一个功能后，只要控制权、执行形态或终止条件不同，句子结构和技术词也应随之变化。

**Bad Case**：因为上一份报告出现过循环、DAG、状态机或流水线，就把同一说法复制到新功能；或者只把功能名替换掉，仍使用相同主语、相同控制结构和相同判定条件。此类输出即使语法通顺也必须退回 evidence 阶段。

机械自检不止比较首句，还比较每个功能的完整因果主链。先把仓库名、功能名、符号名和路径替换成占位符，再对 `公开输入 → 决策 → 转换 → 状态 → 下游 → 输出` 做结构比较：

- 如果两条主链只替换了业务名词，必须回到 evidence 对比 `control_locus`、`execution_form`、`decision_predicate`、`state_carrier`、`termination`；
- 至少两项必须存在当前源码支持的实质差异，否则应合并功能，或围绕真实差异重写，而不是保留两章模板文案；
- 同一功能内，正文是唯一完整主链。表格只能写判定矩阵/边界，图只能压缩角色和路径，不能再次逐项复述正文。

完整章节级 Good / Bad Case 见 [narrative-good-bad.md](narrative-good-bad.md)。必须在写第一章前完整读取，并用其中的三项自检检查每个章节。

### 写作前硬检查

- 是否已经能不用函数名，连续说明“一份输入如何得到结果”？
- 所有“动态、自动、智能”是否都有规则矩阵，而不是只有结果描述？
- 是否分清 Prompt 建议、Schema 校验、调度器算法和运行状态机四个层次？
- 若声称 LLM “生成” DAG/计划，是否明确说明 Prompt 的输入、结构化输出字段、模型生成准则、代码校验边界，以及没有确定性拆图算法这一事实？
- 第一段出现的执行形态、判定字段和专有名词是否都能在当前 evidence 中逐项定位？是否误用了其他报告的样例词？
- 第一段和主链中的 Leader/Coordinator/Agent/Worker/phase/child/node/router/SDK 等词，是否已经说明对象粒度、创建/读取点、真实触发与非行为？若名字暗示的能力并不存在，是否已经明确否定？
- 流程图之前是否已经出现完整自然语言解释？
- 删除规则表和图后，正文是否仍能独立讲清输入如何成为输出；恢复这些内容后，是否只增加规则/视觉信息而不重复正文？
- 核心功能的同类实现对照是否比较运行语义而非功能清单，并保持客观而不替用户做选择？
- 本功能的 `surface_id` 是否与产品表面账本一致，所有核心表面是否都在某一章得到结果级解释？
- 管理面上的配置是否已追到当前执行链真正的 loader/consumer，还是只能标为元数据/目录/未知？
- 是否把同仓库中存在但当前入口未调用的 DAG、协议、存储或外部 adapter 错写成本功能机制？
- `01-project.md` 是否真正包含“用户能直接体验的业务功能”和“核心功能有哪些”两个非空正文章节？
- 每个核心功能是否都在任何 Mermaid、代码链和组件表之前，用至少 3 段连续自然语言讲清一次完整执行？
- 第一张图全部删除后，读者是否仍能回答“输入是什么、谁按什么规则处理、中间状态在哪、何时结束、结果给谁”？

任一答案为否就停在 evidence 阶段，准确记录缺失源码；不要生成看似完整却无法说明实现事实的章节。

## 恢复与耗时

每阶段开始、结束时记录 wall time 到 `performance.md`。已经存在的阶段只有在源码身份与其输入未变化、章节合同仍满足时才复用。某个功能失败时保留其他功能文件；再次执行只补失败项。不得为“变好”而重复启动模型审校。
