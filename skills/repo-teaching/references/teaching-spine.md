# 教学主线设计（spine）

写稿前先完成本设计，写入 `stages/02-spine.md`。设计字段：

## 必填字段

- **本集唯一核心知识点**：一句话。判断标准——观众看完能复述的那句话。装不下两个知识点就拆集。
- **目标观众与前置假设**：观众是谁（如"用过 Claude Code 但没配过 hooks 的开发者"）、默认他们已经会什么。
- **痛点场景**：一个具体、有画面感的场景（谁、在做什么、卡在哪）。必须真实，优先取仓库 issues/文档/常见误用。
- **主比喻**：一个生活化比喻，非程序员也能懂。要求：喻体先讲完整、再落技术点；一集只用一个主比喻。
- **三个展开场景**：每个场景给出 ①痛点 ②做法（来自 evidence 的命令/配置）③数字佐证。三个场景要有递进或并列逻辑，不是随机罗列。
- **演示案例**：仓库最普适的功能，能 3–4 步口述推演完。
- **坑（至多 3 个）**：每个坑带解决办法；优先真实陷阱（版本差异、配置冲突、性能拐点）。
- **收尾三点**：与三个展开场景一一对应的一句话回顾。
- **下集钩子**（系列稿必填）：与本集的关系用一句"如果说 A 是……那么 B 就是……"勾连。

## 系列稿的递进规则

- 第 1 集永远是"跑起来"：安装 + 最小可用示例 + 验证生效的方法；
- 之后的每一集解决"跑起来之后第一个会撞上的问题"，按真实使用顺序递进，不按目录结构平铺；
- 每集开头一句前情回顾，结尾一句下集预告；系列大纲写入 `00-系列大纲.md`，列出每集标题（"主题词 — 利益点"模式）、核心知识点、依赖的上一集；
- 系列总长建议 5–8 集；超过就合并相邻知识点或砍掉低价值集。

## 知识点选择优先级

从 evidence 中按以下优先级选核心知识点：
1. 项目的公开主价值（README 第一段承诺的事）；
2. 用户旅程中必经的决策点（安装方式、配置项、模式选择）；
3. 决定运行范式的机制（它是怎么工作的）；
4. 高频坑与边界（什么时候不该用它）。

health、登录、普通 CRUD、部署 helper 不单独成集。
