# 融合功能章节合同

每个核心功能使用以下顺序；业务介绍和底层机制不得拆到两个远离的章节。整章只允许一条完整因果主链，采用总—分—总；规则、图和表只补充正文没有的新信息。

```markdown
# {业务功能名}

{直接给出当前功能结论：系统作用 + 执行本质 + 决定结果的关键条件。可自然使用“简单来说”，但不得把本说明或上一份报告的句子当模板。}

## 这个功能到底是什么

先不用源码术语回答：谁在什么场景使用；提交或操作什么；系统替他完成哪一整件事；最后在界面、API、文件、消息或外部系统中看到什么；这个名字容易让人误以为支持、但当前实现明确没有什么。至少举一个贯穿后续主链的具体输入例子，但不得虚构仓库没有的数据。

## 这项功能包含什么

用 3–7 条短句列出已被产品表面账本证明的子功能和 `surface_id`。这是覆盖边界，不是按代码目录平铺模块。若同名管理页、目录项或协议入口只有元数据，在这里立即标注“可配置但未接入当前运行时”。

## 先用自然语言讲清运行原理
**本节必须出现在组件表、代码链和第一张流程图之前，也是唯一完整叙述主链的位置。**用连续散文讲完一次真实运行；段数、字数和步骤数不设上下限，以信息闭包为唯一判定：

先从 evidence 的逐跳因果账本写正文，不从组件清单改写。每一个真实交接都要讲“收到什么 → 读取什么 → 为什么这样决定 → 生成/写入什么 → 谁接着用”；段数由交接数量决定。

- 首段说用户/调用方为什么发起、提交什么，系统第一个接手者是谁。
- 中间连续讲每次对象或状态转换。若出现定义、graph、任务、run、message、event、checkpoint、ready queue、外部响应等名词，必须在第一次出现时解释创建者、关键字段和消费者。
- 末段说什么状态何时提交、下游怎样被唤醒、正常/失败/取消如何停止，用户最后得到什么。

如果同一功能包含“定义/配置期”和“实际运行期”，不要硬挤成一条短链：分别写清两个生命周期，再明确哪一个保存对象、版本或稳定 ID 把二者连接起来。生成定义并不等于执行；编译出的展示脚本也不一定是运行事实源，必须以执行器真实读取的数据为准。

这部分必须是报告中最完整、最容易独立读懂的解释；后文的图、表和符号只能补充新信息。若出现“生成器创建 graph、validator 规范化、scheduler 执行”一类压缩句，却没有说明 graph 的字段、校验后的变化、保存位置、调度输入、ready 判定和结果提交，就判定为未讲清。自然语言只把符号链中的函数名换成中文动词也不合格。

### 实现术语闭包（正文不显示这个标题）

在 evidence 中先列出正文要使用的关键名词。每个名词第一次进入正文时，必须自然地补齐七件事：

1. **它是什么**：具体对象、Schema 字段、枚举或进程角色，不用抽象同义词循环解释；
2. **谁创建**：用户、模型、确定性代码、数据库还是外部系统；
3. **谁读取**：哪个执行器、调度器、路由器或 adapter；
4. **读取什么字段**：真正参与判断的数据，不只写对象名称；
5. **触发什么**：读取后启动哪次执行、状态变化或外部副作用；
6. **不触发什么**：名称容易令人误解但源码没有的能力，必须明确排除；
7. **运行底座**：自研代码、具体 SDK/框架、标准协议与网络/进程位置。

例如角色被命名为 Leader，只能在源码证明后才写“拆任务/委派/汇总”；若它只是无显式选择时的默认 `agentId`，必须直说“Leader 只提供默认 ID，本次只执行一个 Agent，不会继续唤醒其他成员”。`phase`、`child` 等层级词也必须说明哪个是业务阶段容器、哪个才是可执行步骤、依赖挂在哪一层、并发配置控制哪一层。以上只是判定方法，正文仍须使用当前仓库的真实名称和事实。

### 机制指纹

写正文前在 evidence 中确定，正文不显示字段名：

- **业务作用**：这一功能在整个系统中接住哪类输入、交付什么用户结果；
- **控制权**：确定性代码、模型、人工、配置或外部服务中，谁决定下一步；
- **执行形态**：循环、状态机、图、流水线、事件、队列、存储检索或源码证明的其他形态；
- **核心判定**：真正控制继续/路由/选择/完成的字段或事实；
- **状态载体**：运行中间事实保存在哪里；
- **终止与结果**：何时收束，谁得到什么。

第一句必须由这些事实生成。比如只有源码证明是循环且存在对应判定字段时，才可以写“这是循环并按某字段决定继续”；只有源码证明由模型读候选和约束产生图时，才可以写“模型生成图”。示例只说明推导方式，不是可复制文案。

## 生成、选择与执行规则
只列正文没有充分表达的决策规则：候选从哪里来、什么条件纳入或排除、如何排序或分配、如何验证、失败是否降级、运行中能否改动。若某项由 LLM 产生，必须先写清“目标/候选/约束如何组成 Prompt → LLM 返回哪些结构化字段”，再分开写“模型被要求遵守的语义准则”和“宿主代码强制执行的确定性规则”。表格不能复述主链上的状态变化。

## 一次完整运行怎么走
直接放真实 Mermaid 交互图和一段读图顺序；**不再用 5–10 步列表复述主链**。图只能压缩已经讲清楚的内容，不能承担首次解释。

## 配置如何真正影响运行

| 配置项 | UI/API 收集字段 | 默认/校验 | 持久化 | 运行时 loader | 执行器消费点 | 真实影响 | 支持边界 |

## 多参与者与外部系统如何协作

若该功能涉及群组、多 Agent、Worker 群、工作流或外部 IM，必须用自然语言说清：成员可以是谁、默认执行者如何决定、单选/多选怎样路由、是并发广播还是依赖调度、参与者是否互见中间结果、有无结果综合器、部分失败如何传播。若宣称是外部 IM，还必须证明 provider adapter、身份、收发链和外部消息 ID。不涉及时说明不适用，不强行增加空表。

## 状态与控制流
分别回答存储/查询、循环与终止、路由条件、并发依据、Worker 交接；不存在就明确写“不存在”。

## 难点与失败方式
说明真正难点、不变量、异常路径和恢复边界。

## 同类项目的对应功能怎么实现
只在能找到官方文档或源码时，与至少 2 个真实框架/项目对照控制权、动态发生时机、路由/依赖、持久化和失败恢复。当前仓库结论来自源码；外部实现必须附一手链接。只描述“各自怎么实现”和客观差异，不给推荐、排名或“应选谁”的结论。无一手来源时直接说明未对照，不影响当前实现讲解。

## 为什么这样设计
根据当前仓库约束解释取舍，禁止把竞品营销描述改写为源码事实。

## 实现摘要与证据边界
用 2–4 句完成“总”：用户最终得到什么、当前代码用什么机制做到、主要代价/限制和仍未被源码证明的边界。这里不替用户做技术选择，不输出推荐、排名、“应选”或“不要选”。

## 交给编码 Agent 的实现地图

这一节把当前实现变成可执行的代码阅读与任务地图，但不假设目标仓库的实际路径。先列当前参考仓库各责任边界：

| 实现责任 | 当前文件 | 关键符号/Schema | 实际行为 | 依赖与耦合 |
|---|---|---|---|---|

再按当前实现的依赖给出编码任务分解；用户没有提供目标仓库时，只写责任与输入/输出，不臆造目标文件路径：

| 任务顺序 | 要新建/改造的边界 | 输入/输出合同 | 必须保持的不变量 | 建议单测/集成测试 | 完成证据 |
```

## 核心机制深挖

当某功能决定项目的运行范式、数据流、状态机、工作流、Agent/Worker 编排、实时交互或持久化设计时，把以下内容放在“系统如何得到结果”之后、“一次完整运行怎么走”的图之前。外围页面和普通 CRUD 不强制套用。

### 读者最需要回答的问题

先写 3–5 个具体问题，不写“它是怎么实现的”这种空问题。例如：

1. 这里的 workflow 是静态 DAG、状态机、数据流，还是由模型动态选择下一步？
2. 节点、边、任务、状态分别有哪些类型和约束？
3. 用户在设计器里的定义怎样变成运行时可执行行为？
4. 切换节点、重试或恢复时，哪些状态保留、哪些重新计算？

后文必须逐题回答，不能只列问题。

### 动态机制问题集

不为某个领域或项目写死问题清单。对每个功能，从 evidence 中的业务对象、数据单元、控制结构、执行位置、状态载体、并发/时序和外部边界，动态生成“读者必须知道什么才能复现该功能”的问题集。至少覆盖当前证据实际出现的维度：

- 输入与数据单元的结构、粒度、生命周期和转换方式；
- 静态定义/配置怎样被校验、编译、注册或加载成运行时对象；
- 控制权在哪里，每个分支真正读哪些字段或事件，无匹配时怎样处理；
- 执行是同步、循环、流式、队列、图调度还是其他形态，并发、顺序、背压和中断如何生效；
- 中间与权威状态在哪里，何时可见，切换/重试/恢复时哪些保留或重建；
- 外部系统/协议/模型/人工在哪一步接手，交换什么数据，返回后谁继续处理；
- 正常完成、部分失败、取消、超时和非法输入分别如何收束，用户/下游最后得到什么。

只需回答与当前证据相关的问题，但不得跳过任何已出现的机制维度。问题数、段数和章节长度由实际机制决定，不能用领域关键词、固定问题数或前一个项目的章节骨架来决定。

### 设计范式与替代方案

用表格客观对照当前实现与 2–4 个真实替代方案：各自怎么运行、控制权在哪里、状态和失败边界有什么事实差异。比较必须来自当前源码和外部一手来源，禁止为了凑数虚构差异；不写“为什么应该采用”“推荐谁”或最终选型结论。

### 规则矩阵

核心功能必须给出可用于实现和技术选型的规则矩阵：

| 决策点 | 输入事实 | 确定性规则 | 模型/启发式规则 | 输出/状态变化 | 失败行为 | 源码 |
|---|---|---|---|---|---|---|

规则矩阵至少覆盖：候选生成、合法性校验、选择/路由、调度/并发、完成/停止、失败/恢复。不存在的项写“不存在”，不能空着。模型 Prompt 中的建议不等于程序保证；只有 Schema、validator、状态机或执行器强制的约束才能称为硬规则。

### 核心类型目录

从枚举、Schema、注册表、协议或工厂中列出完整类型。表格至少包含：类型、业务角色、运行时行为、约束。若类型过多，列完整一级类型并解释扩展机制，不能只挑两三个例子。

若类型存在父子层级，必须在表前用自然语言说明每一级的粒度和执行责任。例如顶层是一次工作流，下一层是业务阶段，再下一层是阶段内可执行步骤；不能只把字段名并列后让读者自行推断。

### 静态定义如何变成运行时行为

解释完整转换链，例如“画布 JSON → 验证 → 编译索引 → 注册 handler/tool → 调度器读取 → 产生结果”。先写自然语言，再画图，最后才列符号链。必须说明转换发生在何时、由谁触发、旧行为何时失效、新行为何时生效。

### 代码执行叙事

选择 1–3 条最能决定技术路线的真实运行路径，逐条写成自然语言。这是正文唯一主链，不要再增加同义步骤列表：

1. **入口与输入**：哪个公开 API/事件收到什么结构；默认值何时补齐。
2. **第一次决策**：代码读取哪些字段，按什么 `if`、枚举、Schema 或状态选择分支。
3. **核心转换**：循环/解析/编译/调度具体遍历什么，如何产生中间对象。
4. **状态提交**：内存、数据库、队列、checkpoint 分别写什么；何时对下游可见。
5. **下游唤醒**：谁因哪个事件/状态变化开始工作，并拿到哪些上游结果。
6. **终止与返回**：正常、部分失败、取消、预算/超时分别如何收束。

自然语言之后再附对应符号与行号。禁止逐行翻译代码；必须解释代码为何形成这个业务行为。若某事实已经在因果主链讲清，规则表只能补充边界或判断依据，不能再次说明“先做 A 再做 B”。

### 逐跳完整性门

对主链中每个动词追问“它具体把什么变成什么”。答案若仍只是抽象动词（生成、规范化、物化、调度、执行、持久化、恢复），继续下钻到当前代码真实读取的字段、产生的对象和下一个消费者。直到技术读者能据此定位实现责任、重建输入/输出合同和编写验证测试为止；不是下钻到逐行代码。

以下任一情况必须退回 evidence：

- 一个句子跨越两个以上责任边界，却没有说明中间对象；
- 只列组件名、函数名或类型层级，没有讲数据怎样变化；
- 定义期和运行期混成一句，读者不知道保存什么、运行时加载什么；
- 讲了成功路径但没有失败、人工暂停、取消或最终状态提交；
- 图比正文包含更多关键节点，说明正文没有独立讲清。

### 状态连续性

用表格回答一次切换、重试、恢复或重新编译前后：哪些事实保留、哪些投影重建、哪些临时状态清空、哪些结果累积。若不存在切换，说明状态生命周期的起止点。

### 五层深入

1. **结论层**：一句话说本质。
2. **机制层**：自然语言解释运行过程。
3. **代码层**：关键符号、数据结构和调用链如何对应机制。
4. **设计层**：为什么采用这种做法，以及主要代价。
5. **协议/状态层**：跨模型、跨进程、跨节点或持久化时的不变量。

五层不是重复同一句话；每层必须增加新信息。

## 深度规则

- 第一层给结论；第二层讲运行机制；第三层讲关键源码；第四层讲设计原因；第五层讲协议或状态边界。
- 底层执行说明必须是自然语言因果叙述。先写“用户发起请求后，系统先……；得到……后，再……；如果……则……；最后……”，再在章节末尾列源码证据。
- 禁止用 `Controller → Service → Repository`、`foo() → bar()`、目录清单或代码摘录代替机制解释。它们只能证明已经讲清楚的自然语言结论。
- 术语第一次出现时立刻解释其业务作用。例如不要只写“router 选择边”，要写“router 读取当前状态中的分类结果，按条件选择下一节点；没有匹配项时走默认分支”。
- 角色名第一次出现时说明它有没有规划、委派、再路由或汇总权；若只是默认目标、显示标签或包装器，必须直说。Agent/模型运行必须说明采用的 SDK/框架，或明确是自研循环通过何种标准 API 调模型。
- 有存储必须讲写入、事实源、查询、索引/召回、一致性和删除。
- 任何名称暗示循环、图、调度、路由、规划、协作或恢复的机制，都必须按当前 evidence 说明真实数据结构、控制权、判定规则、状态和终止；不得从名称推断行为。
- 模型 Prompt 只说明模型被要求做什么；Schema/validator 只说明宿主代码能拒绝哪些结构。两者都不得被描述为未被源码证明的业务正确性算法。
- 同类框架对比必须覆盖控制权和运行语义，不能因为产品名称或表面功能相似就归为一类。
- 任何数据媒介、Worker、构建器或运行编排都使用上述动态问题集解释，不按功能名称套用特定领域模板。
- 任何写成“动态”的能力都必须指出动态发生在设计期、启动期还是运行期；不能把可编辑配置误写为运行时动态路由。

## Mermaid 安全规则

- 仅用 `flowchart LR` 或 `flowchart TD`；主链超过 10 条边时用 TD。
- 节点 ID 只用 `N1`、`N2`；显示文字写成 `N1["执行器"]`。
- 路径、点号、括号、斜杠、尖括号只放引号标签。
- 不把所有系统组件塞进一张图；主链、异常链和部署图分开。
- 每张图使用语义 class：参与者 `actor`、控制器 `control`、执行器 `compute`、状态/存储 `state`、外部服务 `external`、结果 `output`。主链使用实线，可选/异常/异步通知使用虚线。
