# 融合功能章节合同

每个核心功能使用以下顺序；业务介绍和底层机制不得拆到两个远离的章节。

```markdown
# {业务功能名}

简单来说，这个功能就是……

## 用户看到什么
谁在什么场景触发，最后得到什么。

## 系统如何得到结果
**本节必须出现在第一张流程图之前。**先完全使用自然语言，逐步解释输入如何变成用户最终看到的结果。每一步必须写清：收到什么、代码读取哪些字段或状态、按什么规则判断、执行什么转换/算法、为什么、写了什么状态、交给谁、何时结束。这里不能只罗列函数、类、文件或调用箭头。

## 生成、选择与执行规则
对所有“自动/动态/智能/编排”能力逐条列规则：候选从哪里来、什么条件纳入或排除、如何排序或分配、如何验证、失败是否降级、运行中能否改动。若某项由 LLM 产生，必须分开写“模型被要求遵守的语义规则”和“宿主代码强制执行的确定性规则”。

## 一次完整运行怎么走
先用 5–10 步业务语言复述主链，再放真实 Mermaid 交互图。图只能压缩已经讲清楚的内容，不能承担首次解释。

## 组件如何分工
| 组件 | 接收什么 | 做什么 | 交给谁 | 事实源 |

## 状态与控制流
分别回答存储/查询、循环与终止、路由条件、并发依据、Worker 交接；不存在就明确写“不存在”。

## 难点与失败方式
说明真正难点、不变量、异常路径和恢复边界。

## 与同类框架相比
与至少 2 个真实框架/范式比较控制权、动态发生时机、路由/依赖、持久化、失败恢复和适用边界。当前仓库结论来自源码；竞品结论必须附官方文档或源码链接。

## 为什么这样设计
根据当前仓库约束解释取舍，禁止把竞品营销描述改写为源码事实。

## 技术选型结论
明确可直接借鉴、需要改造、不要照搬、仍需验证。

## 源码证据
列仓库相对路径、符号和行范围；未知不得补写。
```

## 核心机制深挖

当某功能决定项目的运行范式、数据流、状态机、工作流、Agent/Worker 编排、实时交互或持久化设计时，把以下内容放在“系统如何得到结果”之后、“一次完整运行怎么走”的图之前。外围页面和普通 CRUD 不强制套用。

### 读者最需要回答的问题

先写 3–5 个具体问题，不写“它是怎么实现的”这种空问题。例如：

1. 这里的 workflow 是静态 DAG、状态机、数据流，还是由模型动态选择下一步？
2. 节点、边、任务、状态分别有哪些类型和约束？
3. 用户在设计器里的定义怎样变成运行时可执行行为？
4. 切换节点、重试或恢复时，哪些状态保留、哪些重新计算？

后文必须逐题回答，不能只列问题。

### 设计范式与替代方案

用表格比较当前实现与 2–4 个真实替代方案：怎么运行、适用场景、当前项目为什么采用/不采用。比较必须来自当前功能的约束，禁止为了凑数虚构竞品差异。

### 规则矩阵

核心功能必须给出可用于实现和技术选型的规则矩阵：

| 决策点 | 输入事实 | 确定性规则 | 模型/启发式规则 | 输出/状态变化 | 失败行为 | 源码 |
|---|---|---|---|---|---|---|

规则矩阵至少覆盖：候选生成、合法性校验、选择/路由、调度/并发、完成/停止、失败/恢复。不存在的项写“不存在”，不能空着。模型 Prompt 中的建议不等于程序保证；只有 Schema、validator、状态机或执行器强制的约束才能称为硬规则。

### 核心类型目录

从枚举、Schema、注册表、协议或工厂中列出完整类型。表格至少包含：类型、业务角色、运行时行为、约束。若类型过多，列完整一级类型并解释扩展机制，不能只挑两三个例子。

### 静态定义如何变成运行时行为

解释完整转换链，例如“画布 JSON → 验证 → 编译索引 → 注册 handler/tool → 调度器读取 → 产生结果”。先写自然语言，再画图，最后才列符号链。必须说明转换发生在何时、由谁触发、旧行为何时失效、新行为何时生效。

### 代码执行叙事

选择 1–3 条最能决定技术路线的真实运行路径，逐条写成自然语言：

1. **入口与输入**：哪个公开 API/事件收到什么结构；默认值何时补齐。
2. **第一次决策**：代码读取哪些字段，按什么 `if`、枚举、Schema 或状态选择分支。
3. **核心转换**：循环/解析/编译/调度具体遍历什么，如何产生中间对象。
4. **状态提交**：内存、数据库、队列、checkpoint 分别写什么；何时对下游可见。
5. **下游唤醒**：谁因哪个事件/状态变化开始工作，并拿到哪些上游结果。
6. **终止与返回**：正常、部分失败、取消、预算/超时分别如何收束。

自然语言之后再附对应符号与行号。禁止逐行翻译代码；必须解释代码为何形成这个业务行为。

### 状态连续性

用表格回答一次切换、重试、恢复或重新编译前后：哪些事实保留、哪些投影重建、哪些临时状态清空、哪些结果累积。若不存在切换，说明状态生命周期的起止点。

### 五层深入

1. **结论层**：一句话说本质。
2. **机制层**：自然语言解释运行过程。
3. **代码层**：关键符号、数据结构和调用链如何对应机制。
4. **设计层**：为什么采用这种做法，以及主要代价。
5. **协议/状态层**：跨模型、跨进程、跨节点或持久化时的不变量。

五层不是重复同一句话；每层必须增加新信息。

## 深度规则

- 第一层给结论；第二层讲运行机制；第三层讲关键源码；第四层讲设计原因；第五层讲协议或状态边界。
- 底层执行说明必须是自然语言因果叙述。先写“用户发起请求后，系统先……；得到……后，再……；如果……则……；最后……”，再在章节末尾列源码证据。
- 禁止用 `Controller → Service → Repository`、`foo() → bar()`、目录清单或代码摘录代替机制解释。它们只能证明已经讲清楚的自然语言结论。
- 术语第一次出现时立刻解释其业务作用。例如不要只写“router 选择边”，要写“router 读取当前状态中的分类结果，按条件选择下一节点；没有匹配项时走默认分支”。
- 有存储必须讲写入、事实源、查询、索引/召回、一致性和删除。
- Agent Loop 必须说明它是否真是循环、循环体、继续/停止条件、工具结果如何回填。
- Graph/Workflow 必须说明图如何构建、边如何选择、router 输入输出、静态/动态修改边界。
- 动态 DAG 必须区分：目标分解规则、任务 Schema、依赖生成规则、负责人选择规则、两遍建图、无环/未知引用校验、ready 判定、并发上限、失败传播、结果综合，以及运行期是否允许修图。
- 同类框架对比必须覆盖控制权和运行语义；例如“模型先产计划再由确定性调度器执行”不能与“预定义状态图运行时选边”混为一类。
- Voice 必须说明音频格式、分段/VAD、ASR、LLM/Tool、TTS、回传、打断和背压。
- Worker 必须说明谁提交什么任务、队列/租约、执行、幂等、产物与状态回传。
- UI Builder/Workflow 必须区分“画布显示模型”和“运行事实模型”，说明节点/边定义从 UI 到运行时的转换链。
- 任何写成“动态”的能力都必须指出动态发生在设计期、启动期还是运行期；不能把可编辑配置误写为运行时动态路由。

## Mermaid 安全规则

- 仅用 `flowchart LR` 或 `flowchart TD`；主链超过 10 条边时用 TD。
- 节点 ID 只用 `N1`、`N2`；显示文字写成 `N1["runner.py"]`。
- 路径、点号、括号、斜杠、尖括号只放引号标签。
- 不把所有系统组件塞进一张图；主链、异常链和部署图分开。
