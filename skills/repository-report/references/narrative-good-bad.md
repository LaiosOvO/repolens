# 因果主链 Good / Bad Case

这些例子只说明质量判定，**不是可复制模板**。实际报告必须换回当前仓库的机制指纹与源码事实。

## Good：一条主链只解释一次

> 用户提交待处理对象后，入口先验证身份与输入版本，再把对象转成带稳定 ID 的任务记录。调度器只领取状态为 pending 且租约已到期的记录；Worker 成功提交产物后，以同一事务把任务改成 completed 并写入结果引用，随后发布完成事件。等待方收到事件后读取已提交结果并返回给用户；取消、租约过期与重试只改变这条主链的边界，不另造第二套执行路径。

这段合格，是因为它从输入推进到输出，控制权、判定、状态提交、下游和终止都出现了。后面的表格只应列“租约过期/取消/重试上限分别如何处理”，图只显示参与者与主/异常路径。

## Bad：只替换名词的万能段落

> 系统收到请求后进行校验和处理，接着更新状态并调用下游，最后返回结果。失败时会重试或降级。

这段可套到任何功能：没有真实控制者、判定字段、中间对象、状态载体或终止条件。替换“请求/结果”为“音频/文本”“目标/任务”仍不增加证据，必须拒绝。

## Bad：组件名串联掩盖中间数据

> 生成器创建 graph，validator 规范化节点，materializer 保存定义，scheduler 执行并返回结果。

这句话看似具体，实际仍无法编码：没有说生成器拿到什么、graph 包含哪些决定运行的字段、validator 会拒绝或补默认什么、保存的哪份对象是事实源、scheduler 读取什么依赖、什么时候入 ready、执行结果写到哪里。修复不是增加更多组件名，而是把每次交接展开为“输入对象与字段 → 判定/转换 → 输出对象/状态 → 下一消费者”。

## Good：定义生命周期与运行生命周期分开闭合

> 用户提交目标和运行身份后，构建入口先把该身份当前获授的工具名加入生成上下文；模型返回包含阶段、依赖和步骤绑定的结构化定义。宿主只接受 ID 唯一、依赖存在且无环、工具已授权的定义，并把规范化后的阶段数组与输入/输出 Schema 保存为带稳定 ID 的草稿。此时只产生定义，不执行工具。
>
> 用户以后用这个 ID 发起运行时，运行入口读取草稿中的阶段数组，先写一条 running 记录，再把每个阶段转换为调度节点。调度器只把依赖结果全部成功的节点放入 ready；节点完成后提交输出并唤醒后继，失败则跳过后代。全部节点收束后，运行入口把步骤、trace、最终状态和可见结果写回同一运行记录，再返回给调用方。

这段合格，因为创建期和运行期由“稳定 ID + 被保存的阶段数组”明确连接，每个新对象都有创建者、消费者和停止条件。实际报告必须替换为当前仓库事实，不能照抄对象名。

## Bad：同一主链重复三遍

正文已经完整写了“提交 → 校验 → 入队 → Worker → 回传”，随后步骤列表再次列同样五步，规则表又把五步逐行改写，流程图仍只画同样五个框。这会增加阅读长度而不增加技术选型信息。

修复方法：保留正文作为唯一因果叙事；删除步骤列表；规则表改为正文未覆盖的判定/失败矩阵；流程图增加角色、状态边界与虚线异常，让它承担视觉压缩而非第三次讲故事。

## 每章发布前自检

1. 隐去业务名词后，这条主链是否仍能套到其他章节？若能，补真实判定、状态和终止事实。
2. 与本报告其他章节相比，至少两个机制字段是否有源码支持的实质差异？若没有，考虑合并。
3. 删除表格和图后，正文是否独立完整？恢复它们后，是否只增加新维度而不重复正文？

## Good：配置与运行时真正接线

> 创建操作保存了角色、模型和工具集 ID。会话执行前，loader 用该 ID 读取当前版本并将它编译为 system prompt 与 allowlist；执行器只向模型暴露 allowlist 内工具。所以工具开关从下一轮会话生效，不会修改已在运行的调用。

这段合格，因为它区分了保存、加载、编译和消费四个责任点，也说明配置何时生效。当前仓库没有某一环时，必须删掉该断言并降级支持边界，不得照抄本例。

## Bad：管理元数据被写成运行能力

> 用户可以在页面安装和开启 Skill，Agent 运行时会自动加载对应工具。

如果证据只有 Skill CRUD 与开关字段，而执行器使用另一份固定工具清单，这就是虚假接线。正确说法是“设置可保存，但当前执行链未读取，属于 metadata-only”。

## Bad：看到同仓库机制就拼接因果链

> 群组消息进入后，系统使用仓库中的 DAG 调度器让多个执行者协作。

“有群组入口”与“有 DAG 调度器”是两条独立事实。只有群组入口真实调用/依赖该调度器时，才能拼成一条因果链；否则必须分别说明当前实际路由。
